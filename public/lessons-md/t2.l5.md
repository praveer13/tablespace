# T2.L5 — Hashing Grows Up: Extendible and Linear

_Track T2: Indexing · ~13 min · tablespace_

> A hash index that never rehashes the world: directory doubling, local depth, and the split that touches one bucket.
T2.L4 gave the hash index its honest paragraph — one probe, no order, a specialist — and left a bill on the table: **growth**. A B+tree absorbs growth with the split you already know: one node divides, a separator climbs, the rest of the tree sits perfectly still (T2.L2). A hash table has no separators and no spine. Its naive growth story is a full rebuild, and T2.L4 waved at the fix in one sentence: real engines use *extendible* or *linear* hashing. This lesson is that machinery — two designs for a single trick, growing an index without ever rehashing the world.

---

## The rehash cliff

Static hashing is one line of arithmetic: `M` bucket pages, and key `k` lives in bucket `h(k) mod M`. It works until the load factor crosses the line — then you allocate `2M` buckets and discover the trap: **the bucket assignment depends on the table size.** `h(k) mod 2M ≠ h(k) mod M` for nearly every key, so growth means reading every bucket page and rewriting nearly every entry — and while you do, the index is either offline or lying.

In an in-memory hobby cache this is a hiccup. For an index underneath a running system, it is an outage scheduled by load factor. The design goal follows directly: growth must be **local** — one bucket at a time, everything else untouched, the table online throughout. Both designs below keep that promise; they differ only in what they spend to keep it.

---

## Extendible hashing: a directory buys locality

Fagin et al., 1979. Two moving parts:

- **The directory**: an array of `2^g` pointers, where `g` is the **global depth**. A lookup takes the leading `g` bits of `h(k)`, indexes the array, follows the pointer. The directory is tiny and cache-resident, so T2.L4's "1 probe" survives with a pointer hop in front of it.
- **Local depth**: every bucket owns a prefix of `d ≤ g` bits — all its entries agree on the leading `d` bits of their hashes — and exactly `2^(g−d)` directory entries point at it. When `d < g`, several directory slots **alias** one bucket.

Hold the invariant before the mechanics: local depth `d` means "this bucket is addressed by everything sharing its `d` leading bits." The directory just makes that addressing explicit — `2^g` named slots, many of which can name the same place.

---

## The split that touches one bucket

An insert arrives at a full bucket. The case analysis *is* the design:

1. **local < global — split, don't grow.** Re-deal the bucket's entries by one more bit: half keep the old prefix, half take the twin. Both buckets now have local depth `d+1`. The directory entries for the twin prefix **already exist** — they pointed at the old bucket — so you repoint them and walk away. Total cost: one bucket's entries redistributed, a few pointer writes. The rest of the table never moves.
2. **local == global — double the directory first.** The bucket owns every bit the directory knows how to read; no spare slot exists to address its twin. So the directory doubles: `2^g → 2^(g+1)` entries, and **every pointer is simply copied twice** — entry `i` and its new twin both point where entry `i` pointed. Zero data moves; doubling is a memcpy of pointers. *Then* case 1 applies.

Read case 2 until it stops feeling like cheating, because it is the entire idea: the structure grows by copying **pointers**, and the data pages sit exactly where they were. The directory can double ten times before the bytes involved rival one bucket page. The B+tree grows by pushing a separator up; the hash index grows by pushing a *bit* up — and neither one rebuilds the world.

Steps:
1. Lookup: take the leading global-depth bits of h(k), index the directory, follow the pointer. The array is tiny and cache-resident — the "1 probe" survives with one pointer hop in front of it.
2. Local depth < global depth means ALIASING: bucket A owns the 2-bit prefix 00, so both 000 and 001 point at it. Buckets are addressed, never named — the directory is a pure pointer array.
3. A overflows: split it at local depth 3 — entries re-dealt into 000 and 001 buckets by one more bit — and repoint the two entries. The directory does NOT grow; the rest of the table does not move.
4. B overflows at local == global: no spare entry can address a twin, so the directory DOUBLES — 8 → 16 pointers, each copied twice, global depth 4. Zero data moves; doubling is a memcpy, not a rehash. Only then does B split into 0100 and 0101.

## Linear hashing: growth smeared across the inserts

Litwin's 1980 answer deletes the directory entirely. Buckets are addressed by `h(k) mod 2^level`, and a **split pointer** walks the bucket array in linear order — 0, 1, 2, … — splitting **the bucket at the pointer** whenever the table decides to grow, appending one new bucket at the high end. Buckets below the pointer are read with `mod 2^(level+1)`; buckets above it, still `mod 2^level`. When the pointer completes a full pass, `level` increments and the table has doubled — one bucket per split, the cost smeared across ordinary inserts.

The honest wrinkle: the bucket that splits is the one at the pointer, **not necessarily the one that overflowed.** A hot bucket may wait its turn behind an **overflow chain** — extra pages hung off the bucket until the pointer arrives. Linear hashing trades extendible's directory for occasional extra hops; both keep the same promise: no global rehash, ever. And this is not a museum piece — **Postgres's hash access method is Litwin's design**, split pointer and overflow pages included, which is exactly why it took until Postgres 10 to become crash-safe: the split bookkeeping had to be WAL-logged, and for a decade nobody had done it. (Your own stack has a cousin, too: Redis's dict grows by *incremental rehash* — two tables, a few slots migrated per operation. Same refusal to stop the world, cruder machinery.)

---

> **[isomorphism]** You have seen this exact move one track down. T1's slot array exists so a record can slide around inside its page while the world keeps pointing at **(page, slot)**: stable handle, moveable payload, one indirection that absorbs every change. The extendible directory is the slot array's cousin at table scale — buckets split, twin prefixes appear, pointers get repointed, and *addressing* never changes, because every lookup resolves through the same array of `2^g` handles. **Indirection buys stability.** The next time you design anything that must grow or move beneath a stable reference — a shard map, a vnode table, a service registry — you are reaching for this shape whether you name it or not.

---

## The verdict, held up

All this machinery, and T2.L4's verdict does not budge: hashing destroys order by design, so `>`, `BETWEEN`, `ORDER BY`, and prefix matches remain full scans no matter how elegantly the buckets grow. What the machinery buys is that the specialist's one job loses its cliff: pure point lookups stay one probe at any size, and the table doubles without a stop-the-world rebuild. Defended honestly, in T2.L4's own terms: if your workload genuinely lives in the pure-equality cell — session tokens, id maps, cache front-ends — this is the O(1) structure you want, and now you know its split. The moment you need a range, no amount of directory cleverness will save you; the B+tree from T2.L1 is right there.

---

- **2^g** — directory entries at global depth g (Indexed by the leading g bits of the hash. Doubling it copies pointers, never entries.)
- **1 bucket** — data touched per split (Entries re-dealt by one more bit; the rest of the table never moves. Locality is the whole design.)
- **0 keys** — rehashed when the directory doubles (local == global forces the double: 2^g pointers copied twice. A memcpy, not a rebuild.)
- **still 0** — ranges answered (T2.L4’s verdict survives the upgrade: no order, no BETWEEN, no ORDER BY. The specialist got better at its one job — not at yours.)

**Q1. A static hash table doubles from M to 2M buckets. Why is that an outage and not a tuning event?**
   A. The new buckets must be zeroed before use
   B. The hash function must be re-seeded for the new table size
   C. Doubling is fine — only odd growth factors force a rehash
   D. h(k) mod 2M ≠ h(k) mod M for nearly every key: the bucket assignment depends on the table size, so doubling changes almost every key's home — a full stop-and-rebuild of the index, under load
   Answer: D — The modulo is the trap: every key's address is computed against M. Extendible and linear hashing exist precisely to decouple growth from table size — one bucket splits, or one pointer walks, and nothing else moves.

**Q2. Extendible hashing at global depth 4: an insert overflows a bucket whose local depth is 4. What happens, in order?**
   A. The bucket splits in place; the directory is untouched
   B. Every key in the table is rehashed into a 2^5-entry directory
   C. An overflow chain is hung off the bucket until the next checkpoint
   D. The directory doubles to 2^5 entries — every pointer copied twice, zero data moved — THEN the bucket splits at local depth 5 and its two directory entries are repointed
   Answer: D — local == global means no spare slot can address the twin bucket, so the directory must grow first — and growing it moves no data. (The overflow-chain answer is linear hashing's move: the bucket at the split pointer splits, not necessarily the one that overflowed.)

**Q3. Which of these are true? (Select all that apply.)**
   A. A bucket split with local depth < global depth leaves the directory the same size — existing entries are simply repointed
   B. Doubling the directory rehashes every key but moves no pages
   C. Extendible and linear hashing preserve enough order to serve small ranges
   D. Linear hashing can leave an overflowing bucket waiting behind an overflow chain, because the split pointer — not the overflow — picks the next bucket to split
   Answer: A, D — A and D are the two designs' load-bearing properties. B inverts the headline: doubling copies pointers and touches neither keys nor pages. C is T2.L4's verdict, and it survives everything in this lesson: order is destroyed by design, in every hash scheme.
