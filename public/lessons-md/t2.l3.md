# T2.L3 — The Write-Optimized Counterpoint

_Track T2: Indexing · ~14 min · tablespace_

> Memtables, SSTables, levels, compaction: how LSM trees trade read amplification for write throughput — and why Cassandra, RocksDB, and TigerBeetle all chose them.
The B+tree's design center is **update-in-place**: one row changes, one page is fetched, modified, dirtied, and eventually written whole — plus its WAL record (T3's tax on every mutation). For the workloads that shaped the relational era that trade was correct. Then the write-heavy era arrived: event streams, metrics, click logs, sensor fleets — tables where writes outnumber reads ten to one and the working set laughs at your buffer pool. For those, in-place update is the bottleneck, because every write is a *random* I/O: the page you must modify is wherever it is. In 1996, O'Neil, Cheng, Gawlick and O'Neil published the way out: the **log-structured merge-tree**. The entire move is one sentence: **never update in place.**

---

## The LSM move: every write is an append

Four mechanisms, and each is simple on its own:

1. **Log first.** The write is appended to the WAL — the durability story is T3's, and it does not change. This is the only synchronous disk touch on the write path.
2. **Memtable.** The record lands in a sorted structure in RAM — usually a skiplist (that structure T2.L1 waved off the disk stage; in memory it is exactly right), sized around 64MB in RocksDB's default. Ack the client. Done. No page was fetched, none dirtied.
3. **Flush.** When the memtable fills, write it to disk *whole*, as one sequential pass: an **SSTable** — a sorted run, immutable from birth. The WAL segment it covered can be recycled. A new memtable starts collecting.
4. **Compaction.** In the background, merge sorted runs into bigger sorted runs, keeping the newest version of each key and dropping what time made garbage.

An update writes a newer *version* of the key; a delete writes a **tombstone** — a record that says "dead", which compaction eventually reclaims (T1.L4's promise, collected by a different reclaimer). No page is ever modified. Every disk write is sequential and batched. That is the entire trick — and the rest of the architecture exists to pay for it.

_fig 1 — the write path is appends all the way down; reads inherit the debt_

Components: write (append-only) · WAL (durability · T3) · memtable (sorted · in RAM · ~64 MB) · L0 runs (flushed SSTables · immutable) · L1 (one sorted run · ~10× L0) · L2 · L3 · … (~10× again per level)

Steps:
1. A write is two appends: the WAL record (the only synchronous part — T3 owns that contract) and an insert into the memtable. Ack. Nothing on disk is updated in place, ever.
2. The memtable fills (~64 MB) and flushes: the whole sorted run hits disk in one sequential pass — an SSTable, immutable from birth. The WAL segment it covered is now recyclable.
3. Flush creates debt: every run is one more place a read must look. Compaction is the debt collector — background merges keep the newest version of each key, drop tombstones, and push data down levels sized ~10× apart.
4. A point read checks the memtable, then runs newest-first. A bloom filter per run answers "definitely not here" in ~10 bits per key, so most levels are skipped with zero I/O. Absent keys cost ~0 I/Os; present keys ~1.
5. A range scan cannot use the bouncer: it merge-iterates across the memtable and every overlapping run, resolving versions as it goes. Ordered and correct — but touching more structures the deeper the debt. That is the read-amplification line on the invoice.

## The bill: three amplifications

Every access method pays in three currencies, and honesty requires naming all of them:

- **Write amplification** — bytes physically written ÷ bytes logically written. A B+tree pays at page granularity: update a 100-byte row and an 8KB page goes dirty (call it ~80× before the buffer pool's coalescing, plus WAL). An LSM pays in *rewrites*: compaction merges each byte into the next level again and again, ~10–30× for leveled over the tree's life. The LSM still wins write-heavy workloads — its writes are **sequential and batched**, and sequential I/O at 30× volume beats random I/O at 80× on real hardware. "Write-optimized" describes the *kind* of I/O, not the byte count.
- **Read amplification** — structures touched per logical read. B+tree: ~1 page (top levels cached). LSM: the memtable plus every run that might hold the key — held to ~1 I/O by bloom filters on point reads, but unbounded by runs on scans. This is the currency the LSM spends.
- **Space amplification** — bytes stored ÷ live bytes. B+tree: pages half-to-full, say ~1.2–1.5×. LSM: every overwritten key's stale versions sit on disk until compaction collects them — plus the scratch space a merge needs while running.

The law, worth stating as one: **you can minimize two of the three; the third collects.** The B+tree minimizes read and space and lets write pay. The LSM minimizes write — the I/O-kind sense above — and lets read and some space pay. T2.L4's decision table is just this sentence with numbers filled in.

---

## Compaction: the debt collector

Flush creates debt: each new run is one more place a read must look, one more copy of keys long overwritten. Compaction is the collector, and its strategy is the biggest knob an LSM exposes. Two payment plans dominate:

- **Leveled** (RocksDB's default, LevelDB's design): each level holds *one* sorted run (or disjoint partitions of one), sized **~10×** the level above. When L0 fills, its run merges into L1; when L1 exceeds budget, parts merge into L2, and so on. A byte is rewritten roughly once per level transition → write amp ~10–30×. But a point read consults at most one run per level, and stale versions are evicted aggressively → read amp is the best an LSM gets, and space amp sits near **~1.1×**. Read-friendly, write-taxed.
- **Size-tiered** (Cassandra's default STCS; RocksDB calls it *universal*): let runs of similar size pile up, then merge a whole tier into one bigger run. Each byte is rewritten only when its tier merges → write amp ~4–10×, the floor among practical strategies. But a read must probe *every* run in the tier (bloom filters do the triage), and a full merge needs scratch space up to the tier itself → read amp O(runs), space amp up to **~2×** worst case. Write-friendly, read- and space-taxed.

Same structure, opposite invoices. Choosing between them is not a benchmark you run once — it is the workload interrogation of T2.L4, answered with the three currencies above.

---

## Bloom filters: the probabilistic bouncer

A point read in an uncompacted LSM would touch every run — the read amplification that makes the whole design look silly. The fix is a **bloom filter** per run: ~10 bits per key, a handful of hash probes, and an answer to one question — "is this key *definitely not* in this run?" — with zero I/O. Hold the properties exactly:

- **No false negatives, ever.** If the filter says no, the key is not there. Skip the run, guilt-free.
- **False positives, yes** — ~1% at 10 bits per key. The filter says "maybe", you read the run, find nothing, pay one wasted I/O. Wrong answers never happen; wasted work does.
- **Point reads only.** A range scan merge-iterates across every run in its window — no bitmap can shortcut ordering.

The arithmetic that makes it survivable: a lookup for an *absent* key costs **~0 I/Os** (every filter declines); a lookup for a *present* key costs ~1 I/O for the run that holds it, plus ~1% × the other levels in wasted probes. That is what turns "write-optimized" from a euphemism into a real option for read-your-writes workloads.

---

> **[analogy]** You have met this memory manager. The memtable is the young generation: allocation is an append, collection is frequent and cheap. Compaction is promotion — survivors move down a level, dead versions and tombstones get swept. The deep levels are the old generation: rarely touched, expensive when they are. Even the failure mode is shared. Let compaction fall behind and you get the LSM's version of the GC death spiral — reads probing dozens of runs while the collector rewrites terabytes to catch up. An LSM is a generational garbage collector where the objects are sorted runs and the heap is your disk.

## Who chose it, and what that tells you

The adoption list reads like a workload census:

- **Cassandra / ScyllaDB** — events, time-series, and messages at 10:1 write:read, replicated across nodes. Size-tiered by default (STCS), leveled (LCS) offered for read-heavy tables: the knob is exposed because the workloads differ *per table*.
- **RocksDB** — the embedded engine under MyRocks, TiKV, Flink's state backend, Kafka Streams. Leveled by default, universal for write-heavy column families, bloom filters everywhere, per-column-family tuning: it is a library, so it sells the knobs, not the answer.
- **TigerBeetle** — a financial ledger: an insert-dominated workload at extreme throughput, with correctness under deterministic simulation as a hard requirement. It built its own LSM in Zig with compaction scheduled deterministically. When your writes *are* the product, you pick the structure that never seeks.

And the counter-example is as instructive as the list: Postgres, InnoDB, SQLite — mixed OLTP, read-heavy, update-heavy, buffer pools that cover the working set — all stayed with the B+tree, and they were not wrong. The interrogation that separates the two camps, applied to your own tables, is the next lesson.

---

- **~64 MB** — memtable (RocksDB write_buffer_size) (Sorted in RAM, flushed whole as an immutable SSTable; the WAL segment it covered is then recyclable.)
- **~10×** — leveled growth per level (L1 ≈ 10× L0’s budget, L2 ≈ 10× L1. The ratio drives both write amp and the level count.)
- **~1%** — bloom false-positive rate (At 10 bits per key. False negatives: zero, ever — an absent key never touches a data run.)
- **~2×** — size-tiered space worst case (A full tier merge needs scratch space up to the tier itself. The price of the lowest write amp.)

**Q1. Compaction rewrites an LSM's data many times (write amplification ~10–30× leveled). How can it still out-write a B+tree?**
   A. It cannot — the amplification math means LSMs always write more and therefore lose
   B. Its writes are sequential and batched — WAL append plus in-memory insert on the hot path, flush and compaction in large sequential runs — versus the B+tree's random page read-modify-write per insert; sequential I/O at higher byte volume beats random I/O at lower volume on real disks
   C. It skips the WAL, so each write is one I/O instead of two
   D. Memtables are faster than B+tree pages because they skip concurrency control
   Answer: B — Write amplification counts bytes; throughput counts seeks. The B+tree pays one random page touch per row mutation; the LSM pays zero on the hot path and settles its rewrite debt in big sequential batches in the background. Both still write the WAL — durability is not optional in either camp.

**Q2. Leveled vs size-tiered compaction — which trades what?**
   A. Leveled: one run per level, ~10× growth — the best read and space amp an LSM gets (~1.1×), paid for with ~10–30× write amp; size-tiered: merge whole tiers — the lowest write amp (~4–10×), paid for with O(runs) reads and up to ~2× space during merges
   B. Leveled minimizes write amplification; size-tiered minimizes read amplification
   C. They are two names for the same strategy in different engines
   D. Size-tiered is strictly better — that is why it is the default everywhere
   Answer: A — Same structure, opposite invoices. Leveled rewrites each byte roughly once per level but keeps one run per level to probe; size-tiered rewrites only on tier merges but makes reads touch every run and needs merge scratch space up to the tier's size. The choice is the workload interrogation of T2.L4, not a default you inherit.

**Q3. A point lookup for a key that does NOT exist, in a 6-level leveled LSM with bloom filters on every run, costs approximately:**
   A. 6 I/Os — one probe per level
   B. ~0 I/Os — every filter answers "definitely not here"; false negatives are impossible, so an absent key is rejected without touching a single data run
   C. 1 I/O — the deepest level must always be checked
   D. It depends on whether the memtable is full
   Answer: B — This is the bouncer's whole job: absence is provable from ~10 bits per key in RAM. The present-key case costs ~1 I/O (the run that holds it) plus ~1% × the other levels in false-positive probes. And note what filters cannot do: a range scan still merge-iterates across every run in its window.

O'Neil, Cheng, Gawlick, O'Neil, "The Log-Structured Merge-Tree (LSM-tree)" (1996) is the founding paper — short, and clearer than most of its successors. Petrov's *Database Internals* chapter 7 covers the modern architecture, and the **RocksDB wiki** (rocksdb.org/docs) is the operator's manual: "Leveled Compaction", "Universal Compaction", and "Bloom Filter" are the three pages to read before touching a production knob. Dayan, Athanassoulis, Idreos, "Monkey: Optimal Navigable Key-Value Store" (SIGMOD 2017) shows how to allocate bloom bits optimally across levels — the reason modern engines spend more bits on the shallow ones. Cassandra's docs describe STCS/LCS in production terms, and TigerBeetle's design docs walk a from-scratch LSM built for deterministic compaction. When T3 makes all of this durable, notice that the WAL was already here: the L in LSM and the L in "log first" are the same letter.
